# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A [FastRAMQPI](https://github.com/OS2mo/fastramqpi) OS2mo integration that
generates four SafetyNet reports (CSV) and uploads them via SFTP:

1. Engagements report for the ADM (administrative) organisation
2. Org unit report for the ADM organisation
3. Association report for the MED (works-council) organisation
4. Org unit report for the MED organisation

The reports are triggered over HTTP (`POST /trigger`), not via a CLI. Data is
read from OS2mo through a typed GraphQL client generated by `ariadne-codegen`.

The project follows the same structure as
[os2mo-sdtool-plus](https://github.com/OS2mo/os2mo-sdtool-plus).

## Architecture

- `safetynet/main.py` — the entrypoint. `create_fastramqpi()` builds the
  `FastRAMQPI` app (passing `graphql_client_cls=GraphQLClient`,
  `graphql_version=GRAPHQL_VERSION`), registers the HTTP router, and
  `create_app()` returns the ASGI `FastAPI` app (used by `uvicorn --factory`).
  The `POST /trigger` endpoint runs the report generation.
- `safetynet/safetynet.py` — the business logic (all `async`): recursive OU-tree
  walkers (`process_adm_unit` / `process_med_unit`), per-engagement/association
  processing, the pydantic row models (`AdmEngRow`, `AdmOuRow`, `MedAssRow`,
  `MedOuRow`), CSV serializers, SFTP upload, and the `generate_reports`
  orchestrator.
- `safetynet/config.py` — `SafetyNetSettings` (pydantic v1 `BaseSettings`). It
  embeds FastRAMQPI's own settings under a `fastramqpi` field.
- `safetynet/depends.py` — FastAPI dependency-injection annotations:
  `GraphQLClient` (from FastRAMQPI's app context) and `Settings` (from the user
  context populated by `add_context`).
- `safetynet/types.py` — `CPRNumber`, referenced by the ariadne CPR scalar.
- `safetynet/autogenerated_graphql_client/` — the generated MO GraphQL client
  (see below).

### Source-system strategy (OPUS vs SD)

Manager engagement resolution differs by source system and is the main branching
logic — see `get_manager_eng_user_key_and_cpr`:

- **OPUS** (`get_opus_manager_eng_user_key_and_cpr`): if a unit's manager is the
  employee themselves, it re-queries the *parent* unit's manager
  (`GetParentManager`).
- **SD** (`get_sd_manager_eng_user_key_and_cpr`): resolves the manager engagement
  via `engagement_response`, or falls back to matching against
  `allowed_sd_engagement_types`. SD user_keys carry an InstitutionIdentifier
  prefix (e.g. `XY-12345`) stripped by `_remove_sd_user_key_prefix`.

## GraphQL client (ariadne-codegen)

- Named operations live in `queries.graphql` (repo root); the MO schema is
  `schema.graphql` (repo root, fetched from a running MO:
  `curl -O http://localhost:5000/graphql/v30/schema.graphql`).
- `safetynet/autogenerated_graphql_client/` is generated and **must not be
  edited manually**. Regenerate with `ariadne-codegen client` (the tool is in the
  `dev` poetry group) whenever `queries.graphql` or `schema.graphql` changes.
- The generated client is passed to `FastRAMQPI(graphql_client_cls=...)`;
  FastRAMQPI instantiates it (authenticated, reusing its MO httpx client) and
  stores it in context under `"graphql_client"`, injected via
  `depends.GraphQLClient`.
- **Bumping the GraphQL version**: update `GRAPHQL_VERSION` in
  `safetynet/main.py`, re-fetch `schema.graphql` at the new version, and
  regenerate. Responses are typed pydantic models; the
  `ShorterResultsPlugin` unwraps single-top-field queries to that field's value.
- The generated package is excluded from ruff (`tool.ruff.extend-exclude`) so
  formatting never fights with regeneration.

## Settings

Configured via environment variables. OS2mo connection settings are nested under
FastRAMQPI with the `__` delimiter: `FASTRAMQPI__CLIENT_ID`,
`FASTRAMQPI__CLIENT_SECRET`, `FASTRAMQPI__MO_URL`, `FASTRAMQPI__AUTH_SERVER`, etc.
Application settings are top-level: `SAFETYNET_ADM_UNIT_UUID`,
`SAFETYNET_MED_UNIT_UUID`, `SOURCE_SYSTEM` (`opus`/`sd`), `INCLUDE_MANAGER_CPR`,
and the SFTP block `SAFETYNET_SFTP__HOSTNAME` / `__PORT` / `__USERNAME` /
`__PASSWORD`.

## Commands

Poetry-managed (`package-mode = false`), Python `^3.12`.

```bash
poetry install                       # all groups
poetry run pre-commit run --all-files # ruff, mypy, deptry, reuse, commitizen
ariadne-codegen client               # regenerate the GraphQL client
```

Run the app locally with the dev stack (requires a separately-running OS2mo, see
https://github.com/OS2mo/os2mo):

```bash
docker compose up --build --detach
# then: curl -X POST 'http://localhost:8000/trigger?skip_upload=true&only_adm_org=true'
```

`skip_upload` writes CSVs to `/tmp/*.csv` instead of uploading via SFTP;
`only_adm_org` skips the two MED reports. `FastRAMQPI` also provides `/`,
`/health/live`, `/health/ready`, and `/metrics` for free.

## Testing

Tests are split into unit tests (`tests/`) and integration tests
(`tests/integration/`, marked `@pytest.mark.integration_test`). `asyncio_mode`
is `auto`. Prefer integration tests over unit tests, and avoid mocks.

- **Unit tests** are pure-function tests (CSV serialization, user-key parsing).
  Note: importing `safetynet.safetynet` requires the generated client to exist,
  so run `ariadne-codegen client` first.
- **Integration tests** run against a live OS2mo stack and use the FastRAMQPI
  pytest plugin's fixtures (`mo_client`, `test_client`, and the auto-applied
  integration fixtures). `tests/integration/conftest.py` overrides the required
  `app` fixture and builds an authenticated `graphql_client`.
  - The auto-applied `os2mo_database_isolation` fixture resets MO to an *empty*
    (migrated but unpopulated) database before every test, so each test starts
    from nothing and seeds everything it needs via the `_testing__*` operations
    in `queries.graphql` (which wrap the real MO `*_create` mutations): first the
    root organisation (`root_org`), then the facets and classes (`class_uuids`,
    driven by `MO_CLASSES`), then its own small ADM tree at the root of the
    org-unit tree. Nothing may be looked up from MOs own fixture data, since the
    reset wipes it.
    - Note the reset truncates the *shared* MO database. Running the integration
      tests against a dev stack destroys whatever that stack had loaded; re-run
      the stack's fixture loader (and this repo's `mo-init`) to get it back.
  - `test_trigger.py` has a dedicated tree for each source system: OPUS (manager
    engagement number taken verbatim from the OU manager's user_key) and SD
    (`XY-` InstitutionIdentifier prefix stripped, manager resolved via
    `engagement_response`). A `@pytest.mark.source_system("opus"|"sd")` marker
    tells the `app` fixture which `SOURCE_SYSTEM` to build the app with.
- The FastRAMQPI integration fixtures require a broker and a database even though
  the app is stateless. Rather than run our own, the `safetynet` service in
  `docker-compose.yml` reuses the OS2mo stack's backing services (as the
  `.integration-test:mo` CI template does): `FASTRAMQPI__AMQP__URL` points at the
  `msg-broker` and `FASTRAMQPI__DATABASE__*` at MOs `mox-db` Postgres (the `mox`
  role is a superuser, which the fixtures use to create/drop per-test template DBs).
- Never run `pytest` directly on the host. Always use
  `docker compose run --rm safetynet pytest ...`.

  ```bash
  docker compose run --rm safetynet pytest -m 'not integration_test'   # unit
  docker compose run --rm safetynet pytest -m 'integration_test' tests/integration/test_trigger.py
  ```
- You need a running OS2mo stack (providing the external `os2mo_default` network)
  for the integration tests. Bring one up from https://github.com/OS2mo:
  ```bash
  git clone https://github.com/OS2mo/os2mo.git && cd os2mo
  docker compose up -d --build   # MO at localhost:5000, Keycloak, msg-broker, fixtures
  ```
  The `dipex` client secret the stack provisions matches `FASTRAMQPI__CLIENT_SECRET`
  in `docker-compose.yml`.
- CI runs unit tests with `-m 'not integration_test'` and integration tests via
  the shared `.integration-test:mo` template (spins up a full MO stack).
